Factory Inventory Management System

A full-stack demo application: a Vue 3 single-page app talking to a Python FastAPI service that serves in-memory data loaded from JSON files. There is no database.

System architecture

Two separately run processes. The browser loads the Vue app from Vite, then the app calls the API directly at http://localhost:8001/api. The URL is hard-coded in client/src/api.js, so Vite does not proxy.

Data flow

How a filter change on the Dashboard becomes updated charts.

  1. User changes a filterFour shared filters live in useFilters: period, location, category and status. They are module-level refs, so every view sees the same state.
  2. View reactsThe Dashboard watches the four refs and reloads. getCurrentFilters() maps them to warehouse, category, status and month.
  3. API client builds the requestapi.js adds a query parameter only when the value is not all, then calls the endpoint with Axios. The Dashboard fetches summary, orders, inventory and backlog in parallel.
  4. FastAPI filters in memoryRoute handlers call apply_filters() and filter_by_month() over lists that mock_data.py loaded from server/data/*.json at startup. Months and quarters (for example Q3-2025) are matched against order_date.
  5. Response is validatedEndpoints with a response_model are checked by Pydantic and serialised to JSON. The dashboard summary is computed on the fly: inventory value, low-stock count, pending orders and order value.
  6. UI re-rendersResponses are stored in refs, and computed properties derive chart series, health metrics and top products. The template re-renders the custom SVG charts.

Restocking flow

How the Restocking tab turns a budget into a submitted order shown on the Orders tab.

  1. User moves the budget sliderRestocking.vue offers $0 to $500,000 in $5,000 steps. Requests are debounced, and a request id makes the view ignore out-of-order responses.
  2. Server recommends itemsGET /api/restocking/recommendations?budget= takes each demand forecast whose forecasted demand exceeds quantity on hand. It sorts by trend (increasing, stable, decreasing) and then by largest shortfall, and spends the budget in that order. The last affordable item may be a partial quantity, and cheaper items further down can still use leftover budget.
  3. Lead time is derived from trendIncreasing is 7 days, stable 10, decreasing 14. An order ships together, so its lead time is that of its slowest item.
  4. User places the orderA confirmation shows total cost and lead time. The view then posts only SKUs and quantities to POST /api/restocking/orders.
  5. Server prices and stores itUnit costs come from server data, never from the client. The server rejects unknown SKUs, empty orders, non-positive quantities and totals above the budget, then appends the order to an in-memory list with an RST- order number and expected delivery date.
  6. Orders tab lists itThe app navigates to Orders, which loads GET /api/restocking/orders into a "Submitted Orders" card. That list is separate from customer orders, so the shared filters and the stat cards do not affect it.

Frontend structure

views/

Page-level components: Dashboard, Inventory, Orders, Demand, Spending, Reports and Restocking. A Backlog view also exists. Orders also shows the Submitted Orders card.

components/

Filter bar, profile menu, language switcher, and detail modals for inventory, products, backlog, cost, tasks and profile.

composables/

useFilters (shared filters), useAuth, and useI18n with English and Japanese locales.

api.js

Single place for HTTP calls. One view, Reports, calls Axios directly instead.

Observations

Worth knowing before you change things

  • Frontend calls endpoints the backend does not have. api.js defines tasks (/api/tasks) and purchase-order (/api/purchase-orders) calls, but the running API exposes neither. purchase_orders.json is an empty list.
  • Restocking cost and stock data is partly placeholder. Only PSU-501 matches an inventory record. The other 8 forecast SKUs have invented quantity_on_hand and unit_cost values in demand_forecasts.json. Lead times are a fixed rule on trend, not supplier data.
  • Filter support is uneven. Inventory ignores status and month; demand and backlog take no filters; total_backlog_items in the summary is never filtered.
  • State is volatile. All data lives in process memory, so a restart resets it, including submitted restocking orders.
  • CORS is open (allow_origins=["*"]) and the API URL is hard-coded. Both are fine for a local demo but need changing for deployment.
  • Backlog view is not routed. Backlog.vue exists but is not registered in the router.
